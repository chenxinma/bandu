## 2. 运行时选型

### 2.1 依赖

```bash
uv add "pydantic-ai-slim[openai-realtime]"   # Agent + Realtime WebSocket 传输（OpenAI 协议）
uv add "pydantic-ai-harness[coder]"          # 运行时能力库（含 Coder 及 Memory/Guardrails/SpendLimits 等）
uv add sounddevice                            # 麦克风/扬声器 I/O（或改用 listentome）
```

> `pydantic-ai-harness` 依赖并安装 `pydantic-ai-slim`；`[coder]` extra 额外带 `json-repair` 与 `ripgrep`。`[openai-realtime]` 单独装，因为 harness 不默认带 realtime 传输。

### 2.2 运行时 = pydantic-ai（Agent 循环）+ harness（能力组合）

Pydantic AI 的定位是三层（见 `llms.txt` / Harness 首页）：

1. `pydantic-ai`：Agent 循环、任意模型、工具、结构化输出、**realtime（speech-to-speech）**。
2. `pydantic-ai-harness`：能力库（Memory / Guardrails / SpendLimits / SubAgents / Skills / 上下文管理 / durable execution）。
3. `Coder` / `Researcher`：能力组合出的完整 agent（示例）。

伴读的教学 agent **不是**编码 agent，因此不直接用 `Coder()` 的 file/shell 工具；但**运行时**基于同一套 harness 能力组合机制，把 S1 需要的运行时能力"拼"出来：

| S1 需求 | pydantic-ai / harness 能力 | 替代的原手写模块 |
|---------|---------------------------|------------------|
| 语音对话闭环 | `Agent.realtime()` + `RealtimeSession` | core.client + voice.* |
| 打断 | `handle_barge_in` / `session.interrupt()` | voice.interrupt |
| 教学规则（软） | `Agent(instructions=...)` | agent.strategy |
| 教学规则（硬） | 事件驱动确定性规则 + `Guardrails` | agent.intent + guard |
| 会话状态/记忆 | `Memory(FileMemoryStore(...))` + Pydantic 状态模型 | agent.state |
| 成本控制 | `SpendLimits` / `UsageLimits` | （原无） |
| 日志/埋点 | `Instrumentation`（OTel）/ Logfire | core.logging |
| 弱网降级 | realtime `reconnect` 策略 + 方案 B（batch STT→text agent→TTS） | session.degrade |

> `Coder` 的 file/shell 工具 S1 不启用；若 S2 想让 agent 校验学生编程题答案（跑代码），再按需挂 `Coder()` 或 `FileSystem`/`Shell`。

## 4. Provider 集成（本方案最大技术风险）

Token Plan 的 `qwen-audio-3.0-realtime-plus` 走 **OpenAI Realtime API 协议**（官方 API 参考确认事件与原协议一致）。官方端点：

```text
wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime?model=qwen-audio-3.0-realtime-plus
（Token Plan：{WorkspaceId} = token-plan）
```

鉴权头：`Authorization: Bearer <KEY>`，可选 `x-dashscope-dataInspection: disable`（关闭数据检测，未成年人合规相关）。首选复用 `OpenAIRealtimeModel`，把 provider 指向该端点：

```python
from pydantic_ai.realtime.openai import OpenAIRealtimeModel, OpenAIRealtimeModelSettings
from pydantic_ai.providers.openai import OpenAIProvider

model = OpenAIRealtimeModel(
    "qwen-audio-3.0-realtime-plus",
    provider=OpenAIProvider(
        api_key=os.environ["TOKEN_PLAN_API_KEY"] or os.environ["ANTHROPIC_AUTH_TOKEN"],
        base_url="https://token-plan.cn-beijing.maas.aliyuncs.com/api-ws/v1",  # ← 路径映射待 W1 验证
    ),
    settings=OpenAIRealtimeModelSettings(
        turn_detection={"sensitivity": "high", "silence_duration_ms": 400},
        openai_voice="longanqian",
    ),
    # 模型名不被 Pydantic AI 识别 → 必须显式给 profile：
    #   采样率：输入 16kHz / 输出 24kHz（官方确认）
    #   能力标志：supports_interruption / emits_input_speech_events / supports_output_truncation
    #   按 Token Plan 实际行为填写，字段名以 pydantic-ai API 参考为准
)
```

**与 OpenAI Realtime 协议的差异（影响 Pydantic AI 直连）**：

| 项 | OpenAI 标准 | Token Plan 实际 |
|----|-------------|-----------------|
| WS 路径 | `/v1/realtime` | `/api-ws/v1/realtime` |
| 轮次检测 | `server_vad` / `semantic_vad` | `server_vad` / `smart_turn` / `smart_turn_v2`（推荐） |
| 音色 | alloy / echo… | `longanqian`（默认）/ `longanlingxin` / `longanlingxi` / `longanxiaoxin` / `longanlufeng` |
| 额外头 | — | `x-dashscope-dataInspection` |

**待验证点（W1 必做）**：

1. `OpenAIRealtimeModel` 能否把 `base_url` 映射成 `wss://…/api-ws/v1/realtime?model=…`（路径非标准，可能不直接支持）。
2. `smart_turn_v2` 是 Qwen 特有轮次模式，Pydantic AI 共享 `TurnDetection` 未必能下发；若不能，先用 `server_vad`（与 OpenAI 兼容），`smart_turn_v2` 留待自定义 provider 时启用。
3. `profile=` 采样率/能力标志按 Token Plan 实测填写（官方确认：输入 16k、输出 24k、单声道、PCM16）。

**兜底路径**：若 `OpenAIRealtimeModel` 无法指向 Token Plan 的 WS 路径，实现自定义 `RealtimeModel` 子类（Pydantic AI 提供 `RealtimeModel` 接口 + codec，文档明确"如何实现另一个 provider"），复用其 OpenAI 协议 codec，把底层 WS 换成 demo 里的 `websockets` 连接。这样仍能获得 `Agent.realtime()` 的 agent 循环、tools、capabilities、事件流，只是传输层自写。

> 鉴权不变：优先 `TOKEN_PLAN_API_KEY`，其次 `ANTHROPIC_AUTH_TOKEN`；Key 只读环境变量，不展示、不落盘、不进日志。

### 4.1 W1 实测结论（headless 烟测，无需麦克风）

用 TTS 合成的“学生提问”音频帧灌进会话（合成语音 → 转写 → 音频回复 → 抢话打断 → 规则硬兜底），W1 必做验证项结果：

| # | 验证项 | 结论 |
|---|--------|------|
| 1 | `base_url` → `wss://…/api-ws/v1/realtime?model=…` | ✅ 直接可用，不需自定义 `RealtimeModel` 兜底 |
| 2 | `profile=` 采样率与能力标志 | ✅ 入 16k / 出 24k；`supports_interruption`、`emits_input_speech_events`、`supports_output_truncation` 实测生效 |
| 3 | `handle_barge_in` / `RealtimeInputSpeechStartEvent` | ✅ 两者均可用；抢话后 0.04–0.22s 停播（含丢弃未播缓冲） |
| 4 | `Guardrails`/`Memory` 在 realtime 下的生效范围 | ⚠️ 未验证，S1 不启用；硬兜底走 `rules.py`（不依赖 capability） |
| 5 | `silence_duration_ms` 三档压测 | ✅ 选 **600ms + medium**（下表）；P50/P95 需真人多轮压测，W3 补 |
| 额外 | `smart_turn_v2`（官方推荐）能否下发 | ❌ Pydantic AI 只映射 `server_vad`/`semantic_vad`，且服务端拒 `semantic_vad`；要下发得子类覆盖 `_audio_input_config`。实测转写落定 1.6s（server_vad 0.7s），**暂不采用** |

三档 turn_detection 压测（同一句 5.68s 合成提问 + 一句 3.12s 抢话）：

| turn_detection | 一句话被切成几段 | 首字响应（说完→首音频块） | 转写落定 | 打断停播 |
|----------------|------------------|---------------------------|----------|----------|
| 400ms + high（原默认） | 5 段，且模型抢答半截问题 | 1.7s | 提前触发、转写残缺 | — |
| 500ms + medium | 2 段（仍抢答一次） | 0.89s | 0.5s | ✅ |
| **600ms + medium（选定）** | **1 句 1 段、转写完整** | **0.88–1.48s** | **0.69–0.90s** | **0.14–0.22s** |
| 800ms + medium | 1 句 1 段 | 2.18s | 0.90s | ✅ |

> 首字响应含 600ms VAD 静音窗；扣掉后模型侧首音频约 0.3–0.9s（`first_audio_ms` 埋点实测 371ms），满足 ≤1.2s 目标。
> 规则硬兜底在无进行中回复时调 `interrupt()`，服务端会回 `Conversation has no active response.`：属 recoverable 事件，会话不受影响，不必特殊处理。
> 实测还修正了一处：`session.send(预置引导语)` 是“让模型回复”的文本轮次，模型会改写话术；现改为要求逐字播报，实测引导语原文播出。

## 5. 语音实时会话（S1 W1）

按 Pydantic AI realtime quickstart 的"三件套"组织（`docs/llms.txt` → Realtime → Quickstart）：

```python
async def run(session: RealtimeSession) -> None:
    mic = asyncio.create_task(session.send_audio(microphone_chunks()))  # 麦克风 → 模型
    spk = asyncio.create_task(play_audio(session.stream_audio()))  # 模型 → 扬声器
    watch = asyncio.create_task(rule_watchdog(session))  # 教学规则硬兜底（§7）
    async for part in session.stream_transcripts():
        print(f"{part.speaker}: {part.transcript}")  # 字幕 + 埋点
```

- **音频契约**：采集/播放采样率以 `session.profile` 报告为准（官方确认：输入 16kHz、输出 24kHz、单声道、有符号 16bit PCM）。
- **轮次检测**：优先 `smart_turn_v2`（语义轮次，官方推荐；"嗯/啊"等附和声不打断），fallback `server_vad`（`silence_duration_ms` 400–800 官方推荐区间，是首字响应主要可调项，W1 三档压测）。
- **语速/上下文**：`speech_rate`（0.5–2.0，可放慢照顾学生）、`max_history_turns`（默认 20，1–50）、上下文上限 40960 tokens / 音频 50 轮 / 300 秒。
- **采样率差异**：输入/输出采样率不同（16k 入 / 24k 出），profile 分别报告，采集与播放各用各的。

## 6. 打断（S1 W1）

Pydantic AI 原生支持 barge-in，**替代**手写"本地 VAD → 停播 → cancel"：

**首选：`handle_barge_in=True`**

```python
async with agent.realtime(model).session(handle_barge_in=True) as session:
    ...
```

用户抢话时，会话自动丢弃尚未播放的缓冲音频、截断 provider 侧转录、取消当前回复。打断响应 ≤ 500ms 由"检测到 speech onset → 本地 flush + 取消"构成，不再依赖一次 WS 往返。

**可选：手动控制**（需要自己维护播放位置，用 `session.played_audio_bytes`）

```python
async for event in session:
    if isinstance(event, RealtimeInputSpeechStartEvent):
        await session.interrupt(played_bytes=session.played_audio_bytes)
```

> 官方完整示例的打断链路与本设计一致：`input_audio_buffer.speech_started` → `response.cancel` + 本地清播放缓冲（`player.cancel_playing()`）。依据 provider profile 分支：`emits_input_speech_events`（会发 speech_started）走手动路径；不发的 provider 用 `handle_barge_in=True` 做本地 flush。Token Plan 具体行为 W1 实测后决定走哪条。

## 7. 教学智能体：3 条硬编码规则

### 7.1 两层集成（与端到端模型的矛盾解法）

**第一层：软约束（instructions）**——`Agent(instructions=...)` 写入人设 + 3 条规则：

```text
你是中小学生的学习陪伴助手，不是答案机。
规则1（防跑题）：非学习话题不直接拒绝，温和转回。
规则2（防直接给答案）：任何题目先提示、再追问，不直接报答案。
规则3（追问澄清）：问题描述不清时先问"你卡在哪一步？题目给了哪些条件？"。
回答简洁自然，口语化。
```

**第二层：硬兜底（确定性规则 + 事件驱动打断）**——保证"直接要答案不给完整答案"100% 生效。用一个独立协程监听 `session.stream_transcripts()`：

```python
async def rule_watchdog(session: RealtimeSession) -> None:
    async for part in session.stream_transcripts():
        if part.speaker != "user":
            continue
        intent = classify(part.transcript)  # rules.py：确定性关键词规则，非 LLM
        if intent in (ASK_ANSWER, OFF_TOPIC):
            await session.interrupt()  # 打断模型当前（可能已开始生成的）回答
            await session.send(canned_reply(intent))  # 文本轮次 → 模型按预置引导语播报
```

- `classify()` 是纯 Python 关键词/规则函数（要答案 / 跑题 / 问题不清 / 正常学习），**不调 LLM**，对应计划风险"规则硬编码优先"。
- `canned_reply()` 返回预置引导语（"我们先不急着看答案，你觉得哪个条件还没用上？"）。
- 时序说明：模型可能已先开口，硬兜底用 `interrupt()` 切断，再注入正确引导语，比"只靠 prompt"更可靠。

### 7.2 内容安全

`Guardrails` capability（harness）做输入/输出/工具调用护栏（含内置 secret/PII 检测），对应计划 S1 起"内容安全审核"。

> 注意：`Guardrails`、`Memory` 等 capability 在 realtime 会话中的实际生效范围，需对照 `llms.txt` → Realtime → Capabilities and Hooks 页确认；**W1 验证哪些 capability 在 realtime 下运行**，不能假设全量生效。

### 7.3 模型能力确认（官方文档）

- **Function Calling 支持**：模型可自主判断是否调用工具（`session.update.tools` + `response.function_call_arguments.delta/done`）。这为 S2 的 `record_mistake`（错题本）等 typed tool 铺路；S1 仍用 `rule_watchdog`（事件驱动，不依赖工具）。
- **结构化输出不支持**：realtime 会话不能直接要 `output_type`，与 Pydantic AI realtime 限制一致（结构化归档需工具或 handoff 到文本 agent）。
- **联网搜索支持**：可与 Function Calling 同时启用；S1 默认关闭。
- 系统指令 `instructions` 按官方建议写口语化人设（禁 emoji/Markdown，保证 TTS 自然），即 §7.1 第一层。

## 9. 可观测性与延迟埋点

用 Pydantic AI 内建 OTel 追踪（`Instrumentation` capability）或 Logfire，替代手写 JSON 日志；realtime 有独立的 usage/observability 支持。

| 指标 | 埋点方式 |
|------|----------|
| 语音首字响应 | 首个 `response.audio.delta` 到达时刻 − 用户说完（turn 边界） |
| ASR 识别延迟 | 用户转写完成事件 − 最后一帧音频发送 |
| TTS 首包延迟 | 首个音频块 − 本响应开始 |
| 打断响应 | speech onset 事件 → 播放 flush 完成 |
| 端到端轮次 | 用户说完 → 首音频块出扬声器 |

保留计划要求的字段级日志（session_id / turn_id / intent / rule_triggered / 各延迟 ms），落在 OTel span 属性或 Logfire 上，7 天保留、不落 Key。

> S1 实际落地：`session_log.py` 写 `.bandu-logs/<session_id>.jsonl`（一行一条：ts / session_id / turn_id / event / text / intent / rule_triggered / first_audio_ms），不依赖外部采集端；OTel/Logfire 待需要集中查询时再接。

## 10. 弱网降级（S1 验收项）

Pydantic AI realtime 自带 `reconnect` 策略（`docs/llms.txt` → Realtime → Connection lifecycle）。降级链路：

```text
realtime 会话正常 → 主通道（speech-to-speech）
  └─ 断连/超限 → reconnect 策略重连（可配次数）
       └─ 仍失败 → 方案 B：batch STT → 文本 Agent.run() → TTS → 播放
            └─ 仍失败 → 本地提示音 + 屏幕文本"网络不佳，请稍后再试"
```

方案 B 即 Pydantic AI 文档明确指出的替代路径 **"Batch STT → text agent → TTS"**，已落地为 `pipeline.py`（`bandu --pipeline` 启动）：

- 本地能量 VAD 收句（底噪自适应阈值，800ms 尾静音，开口前留 200ms 余音）
- → `qwen-audio-3.0-asr-flash`（HTTP 整段转写，**非流式**）
- → 同一个教学 Agent 的 `run_stream()`（`qwen3.6-flash` + `enable_thinking:false`，按句切分）
- → `qwen-audio-3.0-tts-plus`（**流式** TTS，走 `wss://…/api-ws/v1/inference/` 的 DashScope 任务协议，句子一到就合成）
- → `sounddevice` 播放

> 修正两处原文假设：TTS 其实**有**流式接口（compatible-mode 的 `modalities:[audio]` 走不通，voice 一律报 invalid；WS 任务协议可用，首包 0.33s）；ASR 确实只有整段接口（WS `task=asr/function=recognition` 返回 `url error`，`/api-ws/v1/realtime?model=qwen-audio-3.0-asr-flash` 无响应）。

### 10.1 方案 A / B 实测对比（同一批合成语音，同口径）

| 指标 | 方案 A realtime（600ms+medium） | 方案 B pipeline |
|------|----------------------------------|------------------|
| 说完 → 开口（首音频） | **0.88–1.48s** | 2.5–2.8s |
| └ ASR | 含在端到端里（转写落定 0.69–0.90s） | 1.1–1.3s（含 0.6s VAD 尾静音），对冲后净 ~0.7s |
| └ LLM 首句 | 含在端到端里 | +0.6–0.7s |
| └ TTS 首包 | 含在端到端里 | +0.5–0.6s |
| 抢话打断 | ✅ 0.04–0.22s 停播 | ❌ 一问一答，不支持 |
| 兜底话术逐字播报 | 靠 prompt 要求，实测生效 | 不过 LLM，天然逐字 |
| 上下文 | 服务端保留 | 客户端 `message_history` 自己攒 |
| 换模型/调教学策略 | ❌ 锁死端到端模型 | ✅ ASR/LLM/TTS 各自可换 |

> 结论：方案 B 慢在整段 ASR（占 2.5s 里的 1.7s），教学可控性换来约 1.5s 的首字延迟。S1 仍以方案 A 为主通道，方案 B 当降级/讲解通道。

### 10.2 ASR 等待：实测成因与两条处置

**Token Plan 没有流式 ASR**，三条路全试过：`/compatible-mode/v1/audio/transcriptions` → 404 Api not found；realtime 端点接 `qwen-audio-3.0-asr-flash` → 只逐帧回 `{}`，不出转写；`qwen3-asr-flash-realtime` → Model not exist。所以整段上传后等全部转写完，是结构性的。

而且它的**服务端排队抖动极大，与音频长短无关**（同一句 2.5s 音频连测）：0.29 / 0.86 / 0.92 / 1.3 / 1.9 / 2.2 / 3.3 / 5.3 / 7.8 / 9.1 / 10.5 / 12.5s。1s 音频也能等 10s，所以分段/边说边转没用。

**已采用：请求对冲。** `transcribe_hedged()` 同时发 `ASR_FANOUT=3` 份，取最先回来的，其余作废（每份都完整计费，上限 = 3 倍 ASR 时长；改回 1 就是单发）。实测净 ASR 中位 ~0.7s，多数轮次“说完→开口” 1.7–2.5s（原 2.5–2.8s 且带 8–13s 尖刺）。局限：服务端整体慢的相位里 3 份一起慢，仍见过 6.2s。

**备选（已测通，未采用）：把 realtime 模型当纯流式 ASR。** `session.update` 里给 `modalities:["text"]` + `max_tokens:1`（服务端认 `max_tokens`，**不认** `max_output_tokens`；`create_response:false` 也会被剔掉），转写在 `speech_stopped` 后 **0.26s** 落定、无抖动，白送的回复只花 1 个 output token（每轮约 108 input tokens，其中 70 是音频）。代价：方案 B 得挂一条常驻 realtime WS（重连自己处理，不像 pydantic-ai 自带 `reconnect`），且 ASR 重新依赖端到端模型——与“三段各自可换”的初衷相左。

> 方案 B 的 VAD 是本地能量门限（方案 A 用的是服务端 VAD），实测两个坑：固定阈值会把声音小的人当静音、尾静音太短会把带停顿的长句切断。现在阈值按环境底噪 20 分位 × 3 自适应（绝对下限 `SPEECH_RMS_MIN`），尾静音 800ms，单句上限 20s；控制台会打 `[听]/[收音中]/[收完]` 三个状态和实际底噪/阈值，换硬件先看这两个数。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| Token Plan realtime WS 路径无法用 `OpenAIRealtimeModel` 直连 | W1 阻塞 | 自定义 `RealtimeModel` 子类（复用 OpenAI codec，自写传输层） |
| harness capability 在 realtime 下不生效（Guardrails/Memory 等） | 硬兜底/内容安全缺失 | 硬兜底改在 `rule_watchdog`（纯事件驱动，不依赖 capability）；内容安全退到方案 B 文本层 |
| 模型"太聪明"绕过 instructions 直接给答案 | 验收不过 | `rule_watchdog` + `interrupt()` + `send(canned)` 硬兜底 |
| 首字响应不达标 | S1 延期 | W1 调 `silence_duration_ms` 压测 + 方案 B 兜底 |
| 非流式 ASR/TTS 与计划"流式"描述不符 | 降级通道延迟高 | 主通道用 realtime 流式；B 通道仅兜底 |
| Key 泄露 | 安全 | 只读环境变量，不展示/落盘/进日志 |
